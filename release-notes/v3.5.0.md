## 更新

3.5.0 让主控台的「导入状态」可以直接吃官方 App 的存档：选一份 `.jsave`，按**内容**认出来之后转成 ATO 的存档分区，和平时导入状态包走同一条路。**地图是完整导进来的** —— 已探索的格子、已揭示的格子、格子笔记跟着一起落位（实测一份第 5 循环的存档：63 格已探索、3 格已揭示、1 条格笔记），不会再出现"导完打开地图，格子全是未探索"的情况。官方存档里 ATO 没有落点的内容（战役 UID、战斗记录、忆识剧场、密语、配装、时间回环、属性上限……）不再被默默丢掉，而是以带前后标识的文字区块写进记录表笔记，重跑不会叠两份。因为笔记是整串替换，导入前会先提示会不会覆盖掉已有的记录表笔记，点取消就整段中止、服务器零改动。记录表的泰坦列表新增「已死亡」字段，每行的「删除」键改成「死亡」键，按一下就把该行数量累加进已死亡数。

## 新增

### 主控台「导入状态」可以直接导入官方 App 的 `.jsave` 存档

- 新增 `assets/jsave-import.js`（`jsave-import/import_jsave.py` 的逐字段 JS 移植：对外是 `isJsave` / `parseJsave` / `convert`，浏览器挂 `window.ATO_JSAVE_IMPORT`，node 走 `module.exports`）与 `assets/jsave-tables.js`（官方枚举与卡名数据表：86 项货舱、41 个 hub、15 个阵营、319 张科技卡英文名、497 个装备卡号，值以 JSON 文本分段存、加载时 `JSON.parse` 一次）。
- `index.html` 按 **`jsave-tables.js` → `jsave-import.js`** 的顺序在 `map/map-data.js` 之后引入（表必须在转换器之前；转换器用 `window.ATO_MAP_DATA` 落地图瓦片），两个文件都带 `?v=20261004-jsave-map`。「导入状态」按钮补了 `title`，`<input accept>` 放行 `.jsave`，但**扩展名不参与判定**。
- **按内容判定**：官方存档的前 3 字节是不透明头（实测 `81 ae 05`），`isJsave(bytes)` 直接看内容，所以改过名的存档照样认，改过名的 ATO 状态包也不会被误判。
- **容忍官方存档的陈旧尾巴**：官方 App 覆盖写入时不截断，JSON 后面可能残留旧数据（实测最多 31KB）。`parseJsave` 用括号/字符串感知的扫描器取「前 3 字节头 + 第一个完整 JSON 值」，并把 `staleTail` 一起回报，而不是把整个文件丢给 `JSON.parse`。
- 转换出来的结果走的是与常规导入**完全相同**的 `applyImportedSections()`，`sectionRevisions` 语义、防抖保存先落盘、失败时本页不切换存档这些行为一字未改。`.jsave` 只转换得出 `dashboard` / `record` / `map` / `technology` / `heroes` 五个分区，`isFullBackup` 传 `false`，**没转换出来的分区不会被清空**；`campaign_cycle` 超出 `c1..c5` 时明确报错而不是导进错循环。
- 常规 ATO 状态包那条路径没有改动：`FileReader` 从 `readAsText` 换成 `readAsArrayBuffer` 只是为了拿到字节，JSON 分支的行为与此前一致，`tests/jsave-import.test.cjs` 里有专门一条用例钉住它。
- 与验证过的 Python 转换器**除地图分区外逐叶子 0 差异**：对象按键集合并、数组按下标、标量 `JSON.stringify` 相等，唯一豁免是 Python `unique_id()` 的毫秒时间戳 id 行；另有 canonical 形式逐行比对。参考实现是冻结快照（`tests/fixtures/jsave/pysnap/`），不会因为 Python 侧后续再改而变成移动靶。地图分区之所以例外，见下面「地图完整导入」一节 —— 那是本轮唯一一处 JS 版**故意**比 Python 版多做的事，测试里额外钉住"Python 已有的部分（`tokens` / `tileVariants`）一个字都没改"。

### 地图完整导入：已探索 / 已揭示 / 格子笔记

- 官方 `maps[0][i]` 与 ATO 该轮地图的第 i 格按**下标对位**（官方格下标 → `map/map-data.js` 的 tileId，形如 `"057"`）。上一版只导了棋子位置、变体面和"最后到访城市"，`expl`（已探索）、`revl`（已揭示）、`note`（格笔记）全都没导 —— 用户导入第 5 循环的存档后打开地图，本来已经开出来的 63 格全部显示成未探索。现在：
  - `expl` → `map...cycles.<循环>.explored["<格 id>"] = true`（实测本档 **63 格**，测试里逐个 id 与官方 `expl` 对照，`expl=false` 的 17 格逐个断言**没有**被写成已探索）；
  - `note` → `tileNotes["<格 id>"]`（字符串；本档 1 格，`026` = `通用指示物`）；
  - `revl` → `previewRevealed["<格 id>"]`，**只写未探索的那些**（本档 3 格：`008` / `065` / `070`）。
- `revl` 的语义结论（规则也写在代码注释里）：官方 `revl` 是**每格一个布尔**（本档 7 格），不是"某一个最新揭示"——ATO 的单值键 `latestRevealedTile`（"最近一次新翻开的板块"）装不下 7 个标志位，也不含顺序信息，所以**不写它、不编造顺序**；能装下集合的只有 `previewRevealed`（"已揭示但还没探索"，渲染时与已探索一样显示正面）。同时 `expl=true` 的那 4 格不写：它们已经由 `explored` 覆盖，ATO 自己在探索时也会删掉这个键。这条规则在"曾经揭示过"和"当前已揭示未探索"两种读法下结果一致，实测旁证是真实 ATO 存档里仇敌停在未探索板块上时，那张板块正是在 `previewRevealed` 里。
- **一格都不许错位**：只有在「官方恰好一张地图 + 读得到该轮 tileId 表 + 格数逐格一致」时才落位，任何一条不满足就**整个地图一个字段都不写**，并在诊断里给人话（`格数不符，未落位` / `读不到 map/map-data.js 里 c5 的格表…未落位`）。上一版在"读不到格表"时会退化成裸序号（`"57"` 而不是 `"057"`），对已探索/笔记这类按格 id 存的数据等于整套键都错，所以这版收紧了守卫。
- 「最后到访城市」（`campaign_stats.city_tile` → `tokens.markers["<格 id>"].last_city`）与棋子位置 / 变体面的落位规则**一字未改**。
- **格上指示物（`toks`）与奖励指示物（`reward_token`）本轮不导入**：`toks` 的长度随循环变（第 2 循环 4 位、第 4 循环 7 位、第 5 循环 8 位），位序与位含义在 5 份样例里没有任何能钉死的证据（位 3 出现在 4 格上、`026` 的笔记写着"通用指示物"但同格 `has_generic_token=false`），猜一个位序等于往用户图上放**错的**指示物；`reward_token` 在全部样例里**每一格**都是默认值 `"Hull"`（连 `has_reward_token=false` 的格子也一样），照写会让 80 格全长出奖励指示物。两者都只记进转换器诊断（`convertWithReport().stats.map_detail.unmapped`，含是哪几格），不做落位。官方 `add_advr`（额外仇敌）同理：ATO 只有一个仇敌位。

### 官方存档里「导不进 ATO」的内容写进记录表笔记

- 官方顶层键里 ATO 完全没有落点的部分不再丢弃，而是以带首尾标识的区块追加到 `record.notes`：
  - 开头 `──────── 官方存档未导入项（由 .jsave 导入生成，勿手改） ────────`，结尾 `──────── 官方存档未导入项 结束 ────────`。
- 区块内容包括：战役 UID / 战役开始时间 / 战役名、战斗记录、忆识剧场 boss 轨道与泪珠·登升核心（含笔记）、密语语言、配装（`loadout_list`）、时间回环、传送门目标、属性上限无落点、属性值无落点、轮次步骤、皮格马利翁、下战斗笔记、资源无对应行、地图格笔记。
- **整块字符上限 4000**（`NOTES_BLOCK_LIMIT`），超限时先砍最长的那条明细、再整行省略，并留下 `（明细已截断，完整内容见导入报告）`；单行值上限 160 字符，列表超过 12 项时留前 8 项并标出总数。
- **幂等**：`stripNotesBlock()` 靠前后标识认出旧区块，重跑（或把生成结果二次导入）先剥掉旧的再追加，不会叠成两份。
- **用户自己的笔记始终在区块之前**：`campaign_notes` 逐条 + `matrix_notes` 解析后的残留行排在上面，生成的区块只追加在后面。
- 本档实测产出 32 行 / 1070 字符，与 Python 版**逐字符相同**（本轮地图侧新增的"未导入"信息**刻意不进这个区块**，否则 `record` 分区就会与冻结的 Python 参考快照产生差异；它只出现在转换器诊断里，见「已知限制」）。

### 导入前提示：记录表笔记会被覆盖

- 导入状态是整份替换 `record` 分区，所以目标战役里手写的记录表笔记会被这次导入带进来的内容整段取代，而且没有自动恢复的入口。现在写服务端之前先摊平比一次，**两边都有笔记且内容不同**才弹 `confirm`：空档没什么可丢的、重复导入同一份存档也不该打扰用户。
- 判定会同时收 `<用户桶>.notes` 与 `<用户桶>.cycleStats.<循环>.notes`：记录表页面改笔记时写的是 `cycleStats.<循环>.notes` 并把顶层那份删掉，只看顶层等于对真实存档永远不报警。桶 key 不一定是 `default`（官方存档写 `default`，页面按账号 id 分桶），旧存档把 `notes` 直接放在 `record` 顶层的形状也认。
- **点「取消」= 整段中止、服务器零改动**：比较发生在 `flushCampaignSave()` 之前，取消时连待写入的防抖保存都不会发生，只弹一句「已取消导入：没有写入任何分区」。

### 记录表新增「已死亡泰坦」

- 新增 `record.deadTitans`（**字符串**、顶层、不按循环）；官方存档的 `dead_titans` 也落到这里。
- 「泰坦」面板新增「已死亡」输入框（`#deadTitansInput`），`normalizeDeadTitans()` 把值归一到非负整数字符串；列表计数行变成 `总数 x/y · 残废 n · 已死亡 m`。
- 泰坦列表每行的「删除」键改为**「死亡」**键（`titan-remove titan-death`）：按一下把该行从列表移除，并把这一行的「数量」累加到已死亡数，`aria-label` 里写明本次 `+N`，按钮 `title` 说明这个行为。

## 已知限制

- 官方「Fated Events」进度与各定数框状态**不在 `.jsave` 里**（存在设备本地），因此无法导入。实测官方存档的 58 个顶层键里没有任何 `fated` / `const` / `hub` / `event` 键。
- 官方 `toks`（格上指示物）、`reward_token` / `has_reward_token` / `has_generic_token`（奖励与通用指示物）与 `add_advr`（额外仇敌）**本轮不导入**：位序/名字到 ATO 指示物 id 的对应关系没有证据（详见上面「地图完整导入」）。这些"有东西没导"的格子只记在转换器诊断里，**没有**写进记录表笔记区块 —— 那个区块属于 `record` 分区，而 `record` 仍要求与冻结的 Python 参考快照逐叶子相同。
- `round_step` 与官方单整数 `pygmalion` 语义未定 / 粒度不同，**不导入**，只在笔记区块里各留一行说明（`轮次步骤：9（语义未定，未导入）`、`皮格马利翁（单整数）：2（粒度不同，未导入）`）。`echo_track` 照常落到 `record.pygmalion` 的回响轨。
- 官方 `evo.evo_boss_count` 虽然已经算进转换器诊断，但还没有写进地图的 `titanXTrackPosition`（上一版遗留，本轮未动）。
- 合并导入时 `record.notes` 仍然是**整串替换**（本次只加了导入前警告，没有改成合并）。建议导入前先点一次「导出状态」备份当前存档。
- 与 Python 参考的深比较需要本机的 `.jsave` 样例（仓库里没有，路径见 `tests/jsave-import.test.cjs` 的 `JSAVE_PATHS`）；机器上没有该文件时，这条用例按 `node:test` 的方式**显式跳过**，不会假装通过。
